# AGENTS.md

Инструкция для AI-агентов и разработчиков, работающих с этим репозиторием.

## О проекте

Веб-приложение для предварительной записи на телефонный разговор (звонок).

- Владелец приложения публикует доступные интервалы (слоты).
- Гости выбирают свободный слот и записываются на звонок.
- Авторизации, личных кабинетов, интеграций с внешними календарями — **нет**.
- Все слоты имеют фиксированную длительность **30 минут**.
- Слоты формируются на **14 дней вперёд** от текущей даты (окно записи скользящее,
  пересчитывается от `now` на каждый запрос — отдельного джоба для "продления" окна не требуется).
- Гость может записаться только на свободный слот, находящийся в пределах окна записи.
- Данные хранятся **в памяти процесса backend** (без БД). Перезапуск backend сбрасывает все данные.

## Архитектура

```
/backend    — Python/FastAPI API сервер, бизнес-логика бронирования, in-memory store
                (backend/Dockerfile — образ для деплоя)
/frontend   — React/TypeScript SPA (Vite), календарь + список слотов + запись на звонок
                (frontend/Dockerfile + frontend/docker/nginx.conf — билд статики и прокси на /api)
/contract   — OpenAPI-спецификация, единый источник правды для API
/docker-compose.yml — сборка и запуск backend + frontend локально/при деплое
```

Frontend и backend взаимодействуют **только** через HTTP API, описанный в `contract/openapi.yaml`.
Любое изменение API начинается с правки контракта, потом — реализации на backend, потом — на frontend.

## Технологический стек

### Backend
- Python 3.12+
- FastAPI — HTTP-сервер, автогенерация OpenAPI из кода синхронизируется с `contract/openapi.yaml`
  (контракт в репозитории остаётся источником правды; при расхождении — правится код FastAPI)
- Pydantic v2 — модели запросов/ответов, валидация
- Uvicorn — ASGI-сервер
- In-memory хранилище: модуль `slots_store` — реализует генерацию слотов на 14 дней,
  выдачу свободных/занятых, атомарное бронирование.
  **Блокировка бронирования занятого слота — обязательное условие**: перед изменением статуса
  слота выполняется проверка `status == free` и запись нового статуса атомарно, под
  `asyncio.Lock` (общий или по слоту), чтобы при параллельных запросах на один слот
  ровно один запрос получал успех (`201`), остальные — `409 Conflict`.
- pytest + httpx (`AsyncClient`) — тесты бизнес-правил и API, включая тест на конкурентные
  запросы к одному слоту (только один должен пройти)

### Frontend
- React 18 + TypeScript + Vite
- date-fns — работа с датами
- react-day-picker — компонент календаря
- Нативный `fetch`, типы — генерируются из OpenAPI-контракта (`openapi-typescript`)

### Контракт
- `contract/openapi.yaml` — OpenAPI 3.0
- Типы для backend и frontend генерируются из этого файла (`npm run generate:types` в каждом пакете)

### Деплой
- Docker (multi-stage builds), docker-compose
- `frontend` контейнер: build через Vite → отдача статики через nginx, nginx также проксирует `/api/*` на `backend`
- `backend` контейнер: python:slim + uvicorn (при желании — за gunicorn/uvicorn workers)

## Бизнес-правила бронирования (обязательны к реализации и тестированию)

1. Длительность слота — 30 минут, слоты не пересекаются.
2. Слоты существуют только внутри окна `[now, now + 14 дней]`. Слоты, дата которых уже прошла, не показываются и не бронируются.
3. Владелец публикует **доступные интервалы** (например, "рабочие часы" на конкретные дни) — из них система нарезает 30-минутные слоты.
4. Слот может быть в одном из статусов: `free` | `booked`.
5. Забронировать можно только слот со статусом `free`, находящийся в пределах текущего окна записи.
6. Повторное бронирование уже забронированного слота — **блокируется**: запрос отклоняется с
   ошибкой `409 Conflict`, статус слота не меняется, новая запись не создаётся.
7. Бронирование должно быть атомарным: при параллельных запросах на один и тот же слот
   успешным (`201`) может быть только один запрос, остальные получают `409 Conflict`.
   Гонки исключаются проверкой статуса и его изменением как одной неделимой операцией
   (см. раздел Backend — `asyncio.Lock`).
8. Отмена брони — уточнить у заказчика, нужна ли (в исходном ТЗ не упомянута; см. раздел "Открытые вопросы").
9. Часовой пояс: все времена на backend храним в UTC, отображение на фронте — в локальной таймзоне пользователя (уточнить, нужна ли фиксированная таймзона владельца).

## API-контракт (черновой набросок, детализировать в openapi.yaml)

- `GET /api/availability?from=&to=` — список доступных интервалов/дней в окне записи
- `GET /api/slots?date=YYYY-MM-DD` — список слотов на конкретный день со статусами `free`/`booked`
- `POST /api/bookings` — создать запись на слот: `{ slotId, guestName, guestPhone }` → 201 с деталями брони либо 409 если слот занят/вне окна
- `POST /api/owner/availability` — (для владельца) опубликовать доступный интервал — без авторизации согласно ТЗ, но стоит явно уточнить у заказчика необходимость минимальной защиты (см. открытые вопросы)

## Открытые вопросы к заказчику

- Нужна ли отмена/перенос брони гостем?
- Как владелец публикует интервалы — через отдельный (незащищённый) экран в том же приложении, или это делается вручную/конфигом? Раз авторизации нет, нужно решить, не будет ли это уязвимостью.
- В какой таймзоне работает владелец — нужно ли фиксировать её на backend, а не полагаться на таймзону клиента?
- Нужны ли уведомления (email/SMS) о записи? В ТЗ не упомянуты — предполагаем, что нет.

## Структура репозитория (план)

```
backend/
  src/
    domain/           # бизнес-правила: генерация слотов, бронирование
    routes/           # HTTP-обработчики (FastAPI routers)
    store/            # in-memory хранилище (slots_store, asyncio.Lock)
    schemas/          # Pydantic-модели
  tests/
  pyproject.toml (или requirements.txt)
  Dockerfile

frontend/
  src/
    components/       # Calendar, SlotList, BookingForm
    api/               # клиент, сгенерированные типы
    pages/
  Dockerfile

contract/
  openapi.yaml

docker-compose.yml
```

## Команды разработки (план, уточнять по мере создания package.json)

```bash
# backend
cd backend && python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn src.main:app --reload
pytest

# frontend
cd frontend && npm install && npm run dev

# генерация типов из контракта
npm run generate:types   # в backend и frontend

# сборка и запуск через docker
docker compose up --build
```

## Правила для агентов при работе в этом репозитории

- Любое изменение API сначала вносится в `contract/openapi.yaml`, затем в реализацию.
- Бизнес-правила бронирования (раздел выше) покрываются тестами в `backend/tests`.
- Не добавлять БД, авторизацию, внешние календари — это осознанно исключено из ТЗ.
- Все даты/время на backend — UTC; конвертация в локальное время — только на frontend.
- При добавлении зависимостей — предпочитать минимальный набор, соответствующий стеку выше.
